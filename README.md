# codex-app-server-java

[English](README.md) | [简体中文](README.zh-CN.md)

An independent, framework-neutral Java client for the [Codex app-server](https://github.com/openai/codex/tree/main/codex-rs/app-server) protocol.

> [!IMPORTANT]
> This project is at the design and bootstrap stage. It is not yet published to Maven Central and does not currently provide a usable client API.

`codex-app-server-java` aims to let Java applications embed the rich, interactive Codex experience without parsing the lossy output of `codex exec --json`. It will manage a local `codex app-server` process, speak its bidirectional JSON-RPC-like protocol, expose typed Java events, and preserve unknown protocol data for forward compatibility.

This is an independent community project. It is not an official OpenAI SDK and is not affiliated with or endorsed by OpenAI.

## Why this project exists

Codex exposes two different integration surfaces:

- `codex exec --json` is a non-interactive JSONL stream intended for scripts, automation, and CI.
- `codex app-server` is the bidirectional interface used to power rich clients. It exposes threads, turns, streamed items, approvals, user-input requests, command output, file changes, plans, token usage, interruption, steering, and persisted conversation history.

OpenAI currently provides a Python SDK that communicates with the local app-server. The TypeScript Codex SDK wraps the non-interactive CLI flow, and there is no official Java app-server SDK today. Java applications therefore need to implement process management, request routing, notifications, server-initiated requests, and protocol-version handling themselves.

This project provides that missing Java integration as a reusable library instead of solving it separately in every application.

## Project goals

- Launch and manage `codex app-server` as a local child process.
- Support the default JSONL-over-stdio transport first.
- Implement the initialization handshake and bidirectional request routing.
- Provide typed Java APIs for threads, turns, items, approvals, and user input.
- Stream message, reasoning, plan, tool, file-change, usage, warning, and lifecycle events without losing their original ordering.
- Preserve unknown methods, item types, enum values, and fields instead of failing when Codex evolves.
- Track the schemas generated by supported Codex CLI versions.
- Offer deterministic fixtures and a fake app-server for downstream contract tests.
- Keep the public API independent of Spring, Reactor, and any particular UI framework.
- Maintain an architecture that can later move into, or be replaced by, an official upstream Java SDK.

## Non-goals

- Reimplementing the Codex agent or model runtime.
- Wrapping the OpenAI REST API. For that, use the official [OpenAI Java library](https://github.com/openai/openai-java).
- Providing a terminal or web UI.
- Defining application-specific transcript, persistence, or presentation models.
- Hiding security decisions by automatically approving every request.
- Treating WebSocket transport as stable before Codex documents it as supported for production use.

## Protocol overview

The app-server protocol is similar to JSON-RPC 2.0, but messages omit the `"jsonrpc": "2.0"` field on the wire.

Requests contain an ID, method, and optional parameters:

```json
{"id":1,"method":"thread/start","params":{"cwd":"/workspace/project"}}
```

Responses contain the matching ID and either a result or an error:

```json
{"id":1,"result":{"thread":{"id":"019..."}}}
```

Notifications have a method but no ID:

```json
{"method":"item/agentMessage/delta","params":{"threadId":"019...","turnId":"019...","itemId":"item_1","delta":"Hello"}}
```

The server can also initiate requests, such as command approvals or structured user input. A correct client must keep reading while a turn is active and route all four message shapes:

| Shape | Meaning |
| --- | --- |
| `id` + `method` | Server or client request expecting a response |
| `id` + `result` | Successful response |
| `id` + `error` | Failed response |
| `method` without `id` | Notification |

Typical lifecycle:

```text
start process
    -> initialize
    -> initialized
    -> thread/start or thread/resume
    -> turn/start
    -> turn/started
    -> item/started
    -> zero or more item-specific deltas
    -> item/completed
    -> turn/completed
```

## Planned architecture

```text
Java application
      |
      v
CodexClient
      |-- request correlation and timeouts
      |-- notification subscriptions
      |-- approval and user-input handlers
      |-- thread and turn lifecycle
      v
CodexTransport
      |-- JSONL/stdio process transport
      `-- future transports behind the same interface
      v
codex app-server
```

The initial repository is expected to contain three modules:

| Module | Responsibility |
| --- | --- |
| `codex-app-server-protocol` | Wire envelopes, typed v2 payloads, unknown-event fallbacks, and schema metadata |
| `codex-app-server-client` | Process lifecycle, stdio transport, RPC routing, retries, subscriptions, and high-level thread/turn APIs |
| `codex-app-server-testing` | Fake server, recorded fixtures, contract-test helpers, and compatibility assertions |

Application-specific normalization remains outside the SDK:

```text
Codex wire event
    -> codex-app-server-java
    -> application adapter
    -> application event model
    -> persistence and UI
```

This boundary allows applications to adopt a future official Java SDK without rewriting their storage or presentation layers.

## Planned API direction

The exact API will be finalized through tests and the first real integration. The intended usage is:

```java
try (CodexClient client = CodexClient.start()) {
    CodexThread thread = client.startThread(
        ThreadOptions.builder()
            .cwd(Path.of("/workspace/project"))
            .build());

    TurnHandle turn = thread.startTurn("Inspect this repository.");
    turn.events().subscribe(event -> System.out.println(event));

    TurnResult result = turn.await();
    System.out.println(result.finalResponse());
}
```

This example documents direction only; these classes are not implemented yet.

## Compatibility strategy

The Codex app-server protocol evolves with the Codex CLI. The CLI can generate schemas matching its installed version:

```bash
codex app-server generate-json-schema --out ./schemas
codex app-server generate-ts --out ./schemas-ts
```

The SDK will use those schemas as versioned compatibility inputs, not as a reason to reject future data.

Compatibility rules:

1. Parse the message envelope defensively.
2. Preserve the complete raw payload for every message.
3. Represent unknown notifications and item types explicitly.
4. Ignore unknown fields when decoding known types.
5. Never silently reinterpret an unknown enum value as a known value.
6. Test each supported Codex CLI version against recorded and generated fixtures.
7. Publish a compatibility matrix before the first stable release.

The stdio transport is the initial compatibility target. WebSocket support may be added later but is currently experimental in Codex.

## Security model

The SDK will not make approval decisions on behalf of an application.

- Applications must choose their sandbox and approval policies explicitly.
- Server-initiated approval requests must be handled or rejected deliberately.
- Child-process environment and working-directory inheritance must be configurable.
- Raw protocol traces may contain prompts, paths, command output, or other sensitive data and must be opt-in with redaction support.
- Closing or timing out a Java request must not leave an active Codex turn consuming resources unnoticed.

## First integration: LoopAide

[LoopAide](https://github.com/rudy2steiner/loopaide) will be the first production-style consumer of this SDK. It currently integrates Codex through `codex exec --json`; the SDK will allow it to move to the richer app-server protocol while keeping its own provider-neutral event, persistence, and UI models.

LoopAide will act as an integration test rather than an application-specific dependency: this SDK must remain usable by any Java application.

- [ ] Implement tolerant message-envelope decoding.
- [ ] Add fake-server and contract-test infrastructure.

- [ ] Manage the `codex app-server` child process.
- [ ] Implement `initialize` / `initialized`.

- [ ] Publish signed artifacts to Maven Central.

- [ ] Open an upstream design issue with real integration evidence.
- [ ] Contribute upstream only if invited under the Codex contribution policy.
- [ ] Keep the public API replaceable by a future official Java SDK.

## Upstream strategy

The project is intentionally structured for eventual upstream alignment. OpenAI's Codex repository currently accepts external code contributions by invitation, so the intended process is:

1. Build and validate the library independently.
2. Use it in a real Java application.
3. Publish protocol fixtures, compatibility results, and implementation experience.
4. Open an upstream proposal before submitting code.
5. Submit a focused pull request only if Codex maintainers invite the contribution.

Possible upstream outcomes include moving the SDK into `openai/codex`, contributing shared conformance fixtures, documenting it as a community client, or replacing it with an official implementation behind the same application boundary.

See the [Codex contribution policy](https://github.com/openai/codex/blob/main/docs/contributing.md).

## Development status

No artifacts have been released. Build commands, dependency coordinates, supported Java versions, and contribution instructions will be added with the protocol foundation.

The planned Java baseline is Java 17 so the SDK can use records, sealed types, and modern concurrency APIs while remaining usable from Java 21 applications such as LoopAide.
